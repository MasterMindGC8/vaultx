# Vault X 1.6.5

File transfers now show transferred bytes, measured speed and approximate time remaining, with separate waiting, saving, delivered, unconfirmed, cancelled and failed states. Estimates appear only after enough recent progress and disappear if progress stalls.

## Changes

- Stream outgoing files from disk instead of loading the whole file before sending.
- Request encrypted recipient receipts; with an updated recipient, send one chunk at a time and report delivery only after the recipient saves the file.
- Keep older recipients usable, with an explicit **Delivery unconfirmed** result instead of claiming success.
- Validate incoming names, sizes, chunk counts, indexes and lengths. Reject conflicting duplicate chunks and isolate received files in generated subfolders to avoid overwriting another download.
- Handle cancellation, expired transfers, disconnections and local save failures. Preserve the selected recipient across asynchronous file selection.
- Stop continuous idle CRT animation while retaining the static terminal appearance. Build conversation rows lazily.
- Fix relay queue ordering, premature packet removal, stalled overflow delivery and concurrent-disconnect failures. Retain ciphertext until acknowledgement or expiry, within bounded RAM.
- Produce Windows installers in the release workflow and run client, native crypto and relay checks.

## Limits and deployment

- **64 MiB maximum per file**, one outgoing transfer and at most two incoming transfers at once. The receiver still buffers chunks in memory; larger files need a separate disk-spooling implementation.
- Confirmed upload progress requires both endpoints to use this update. An older recipient does not provide delivery receipts.
- Failed transfers require resending; automatic resume is not implemented.
- Relay changes require the relay operator to deploy the updated Go server. Installing a client does not change the public relay.
- The per-chunk receipt window bounds queued work but may reduce peak throughput on high-latency connections. No internet speedup or specific CPU/memory reduction has been benchmarked.
- Received files still use ordinary local disk storage. Deletion is not a forensic-erasure guarantee. This remains an engineering scaffold, not a formally audited product.

## Validation

On Windows: 30 client tests, 20 Rust release tests, static analysis, release build and isolated native startup passed. Encrypted loopback transfers used the real Rust session implementation and Go relay; an empty file and a 2,457,617-byte file arrived byte-for-byte intact. Tests also cover malformed transfer data, cancellations, stalls, a narrow progress display, authentication and conversation UI.

Go queue/router tests passed under the race detector. A synthetic vault created by the previous installed crypto library could be opened/written by the new library and reopened by the old one. No real private vaults or conversations were used for these checks.

Release workflow results separately establish builds/startup checks for the distributed platform artifacts. Cross-machine transfers over the public relay still require practical verification after both clients and the relay are updated.
